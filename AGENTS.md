# Development instructions

- Develop a C# Logi Actions SDK plugin and profiles for Ghostty. macOS is the only supported platform for now.
- Always use the latest available official Logitech C# SDK. Before implementation, check Logi Options+ for updates, review https://logitech.github.io/actions-sdk-docs/, and run `dotnet run --project tools/SdkCheck`. The C# SDK is the installed host's `PluginApi.dll`; hosted CI uses the API distributed with the latest pinned official LogiPluginTool when no host is installed. This compatibility build does not prove native host acceptance. a successful NuGet tool check alone does not establish that the host is current. Report when current host freshness cannot be verified.
- Update the local generator with `dotnet tool update logiplugintool --local` when a new stable version is published. Commit the tool manifest and SDK/project changes together. Never vendor the proprietary Plugin API or bundle it in the plugin.
- Match the target framework to the current Plugin API. The validated host 6.4.2.3414 requires .NET 10, newer than the generator's net8.0 default. Keep global.json current with the required .NET SDK.
- Always consider future Windows support in design. Actions depend on `IGhosttyController`; `GhosttyControllerCommon` contains shared behavior, with `GhosttyControllerMacOs` and `GhosttyControllerWindows` for platform-specific behavior. Keep OS selection in the factory. Use inheritance only for actual shared behavior.
- Monitor official Ghostty Windows development during maintenance and SDK reviews. Once an official Windows version becomes available, implement and test Windows support, update package metadata, and add native Windows acceptance. Do not advertise Windows support before validation. The Windows controller currently reports unsupported operations explicitly.
- Keep VS Code ready: update settings, C# tasks, debugger configuration, and extension recommendations whenever the workflow changes. Keep Codex recommended.
- Require at least 90% production line test coverage and 100% translation coverage for each selected language: English (en-US) and Brazilian Portuguese (pt-BR). Never exclude production source to inflate coverage. Keep names, descriptions, and groups translated. Diagnostic logs and developer documentation may remain English.
- Use `./repo check` as the shared quality gate for development, Git hooks, and CI. It verifies SDK tooling, translations using the actual SDK parser, tests and coverage, Release build, packaging, and package verification. Missing reports, empty coverage, missing translations, or failing commands must block the gate. Native device behavior must be tested separately in Logi Options+.
- Use `./repo test`, `./repo coverage`, and `./repo translations` for focused checks. Enable repository hooks with `./repo hooks`. Both pre-commit and pre-push must call the same quality command; never bypass hooks or weaken checks to push.
- Follow Gitflow: develop is the integration/default branch; work on feature/* branches created from develop. Only PRs may put code into develop. No direct pushes, even for initial code. This initial setup remains on feature/initial-setup until a PR is requested.
- Create releases from release/* branches. The main branch will be introduced with the first production version; protect it before accepting code. Release fixes return to develop by PR. Reserve hotfix/* for production fixes and backport by PR. Never publish or create a PR unless requested.
- Before pushing, ensure the checked-out commit is the commit being pushed and the working tree is clean, then run the shared gate. Release tags may only be pushed from release/* at its validated HEAD.
- GitHub develop protection must require PRs and the Quality gate status, including administrators. Main must be protected before the first production release. The release workflow is explicitly authorized to integrate validated release/* code directly into main without a PR; configure a release automation identity permitted by those protections. Never weaken or disable protection during a release. All changes into develop still require PRs. Local hooks complement server-side checks; they do not replace protection.
- English strings serve as SDK localization keys. Keep XLIFF IDs and source strings aligned with compiled actions; update both selected languages together. Never silently substitute pt-PT for pt-BR.
- Build/package operations must not link or reload the installed plugin implicitly. Local linking uses the explicit `EnablePluginLink=true` property.
- Use authentic UI-exported `.lp5` profiles under `src/package/profiles/`; document device and app requirements. Do not invent profile formats or expose personal identifiers.
- Use argument-based process execution. Never interpolate untrusted action input into shell or AppleScript source.
- Ask for clarification when intended behavior is unclear. Do not use em dashes in documentation.

- Every action must have an outlined SVG symbol, preferably from an established permissively licensed open-source icon library, with its license and provenance retained, and a matching recolorable button icon template. Prefer SVG wherever supported. SVG artwork must be hollow, flat, and transparent, without gradients, shadows, or filled mascot bodies. Button templates use a Ghostty-inspired blue background (#149CFF) with white outlined icons; users can recolor them. Use blue/white for plugin branding; SDK action symbols must be monochrome black so Logitech can recolor them. The plugin PNG uses the same blue/white appearance with transparent outer padding, rendered from plugin-icon.svg. Validate action icon coverage in the shared gate.
- The default Ghostty Actions Ring profile has a Settings folder in the top slot containing Open Settings and Reload Settings. Bundle the authentic Options+ export as DefaultProfile72.lp5; updates must not overwrite existing user profiles.

- Releases are always stable. The release dispatch has only a Major/Minor/Fix version increment. Merge validated release code into main automatically without creating a PR to main; return changes to develop through a PR.
